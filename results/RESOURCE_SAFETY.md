# Adaptive Mac resource safety — implementation and limits

Status: `TESTED_CPU` for policy simulation and `INFERENCE_COMPLETED` for the subsequent guarded internal-development runs. The already completed 28-step SFT predates this guard.

## Implemented

- `src/mri_rl/resource_supervisor.py` samples `memory_pressure -Q`, `vm_stat`, `sysctl vm.swapusage`, `ps` and `pmset` with short timeouts. If MLX is already loaded, it also reads supported Metal active/peak allocation counters. Missing thermal, power or process readings are recorded as `SENSOR_UNAVAILABLE`/`null`; no temperature is fabricated.
- The policy requires 3 warning samples, 2 critical samples and 3 clean samples to recover, except an imminent OOM signal below 1% pressure-free and 1 GiB available blocks immediately. A large *absolute* swap total alone never triggers a warning. Swap *growth rate*, pressure and reclaimable memory are considered; low memory requires corroborating pressure. Critical pauses scheduling of the **next** safe unit and samples every 15 seconds until recovery. Warning adds a bounded 5-second cooling interval. It never sends signals or kills another process.
- The current sequential inference runner accepts `--resource-guard` and `--resume`. It samples before model load and between images; each prediction is flushed and `fsync`ed. Resume skips only rows whose record ID, prompt, image checksum, manifest hash, pinned model/config/template, adapter checksum and decoding settings match. A torn final JSONL line is saved as `.partial` before repair. A duplicate ID or changed configuration fails closed.
- Future `mlx_sft_warmstart` invocations gate model load and each optimizer step by default. Each completed step saves an atomically renamed LoRA adapter and fsynced private receipt under `local_data/.../checkpoints/`. The receipt pins model config, train-record hash, seed, step count and microbatch/accumulation metadata. A pre-existing run directory is rejected instead of overwriting progress.
- MRI images, patient-linked raw outputs, resource events and adapter weights remain under ignored `local_data/`; only this aggregate description and code/tests belong in Git.

## Verified signals and simulated policy checks

The guarded 54-question SFT28 matched-prompt inference completed all 54 rows and fsynced each one. Its resource log recorded 55 `NORMAL` and **three `CRITICAL` samples**, all around one early image. Those three were a **false-positive pause caused solely by a transient swap-rate spike**: contemporaneous memory-pressure free was 60–77% and reclaimable memory estimate was about 18–20 GiB, then the run automatically recovered. No generation was lost. A failing regression test reproduced this healthy-pressure swap churn. The policy now requires corroborating low memory pressure or available memory before swap-rate warnings/critical states; the focused safety tests pass. This code correction took effect for subsequent processes, not retroactively for the already running SFT28 inference. The subsequent starting-adapter, image-swap and no-image controls also completed with guarded, incremental output.

A later authorized live sample reported memory-pressure free **76%**, swap used **29.82 GiB**, battery **62% and discharging**, and an estimated **1:06 remaining**. The completed starting-adapter, swap and no-image inference logs contain **55/55**, **25/25** and **25/25** `NORMAL` samples, respectively. No sustained low-memory or thermal incident was observed. `pmset` thermal output sometimes lacks a measurable state; unavailable readings stay explicit. Unit tests simulate sustained warning, critical pause, recovery, declining swap despite high absolute usage, healthy-pressure swap churn, missing sensors and durable checkpoint receipts. No physical stress test was performed.

## Scientific and recovery limits

This supervisor changes pacing only at safe boundaries. It does not change generation length, visual tokens, reward, rollout group size, learning rate or model precision. The resource-event JSONL makes any pause inspectable. Between-step SFT adapter checkpoints are recoverable weights, **not exact training-resume checkpoints**: the current MLX port does not save and validate optimizer or RNG state. Resuming from an intermediate adapter with a new optimizer must be labeled an exploratory continuation; a matched scientific arm must restart from its agreed common starting state. Existing multi-arm GSPO runs use bounded per-group adapter/receipt units and likewise must not be called exact resumes without state restoration. The new inference resume is exact for already completed predictions under its recorded configuration, but an in-progress generation must rerun.

`ps` may be unavailable in a restricted shell, and macOS thermal limits may not be exposed. The sampler records those omissions. The gate cannot interrupt an individual long Metal kernel, heal a hung runtime, or guarantee against sudden OOM. A supervising process may recover the next bounded unit from verified saved weights, but any worker failure still needs inspection of the last durable receipt before relaunch.
