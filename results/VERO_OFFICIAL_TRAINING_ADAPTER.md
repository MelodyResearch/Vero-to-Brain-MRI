## Real MRI adapter and execution

[`vero_train_adapter.py`](../src/mri_rl/vero_train_adapter.py) converted **520** private MSD Task04 image-grounded records into official veRL JSONL, yielding **416** training rows and **104** scan-disjoint engineering dev rows. Each split contains two routes equally: training 208 spatial centroid and 208 anterior/posterior comparison; dev 52 of each. Files and image paths remain under ignored `local_data/msd_task04/vero_training_adapter_v1`. Mask-derived targets are hidden from prompt images. [`vero_mri_reward.py`](../src/mri_rl/vero_mri_reward.py) scores centroid within 3 native voxels or exact dominance, then applies Vero's 0.8 accuracy/0.2 format blend. This is an MRI verifier extension passed to the **official** veRL reward manager, not a replacement trainer. The formatter and coordinate tolerance are our engineering choices, not part of released Vero.

The adapter also consumed **16** fixed-midpoint, image-only, mask-verified prompts from the eight real MSD Task01 multisequence tumor scans: eight enhancing-presence and eight tumor-centroid-grid questions. The combined private veRL files in ignored `local_data/vero_combined_training_v1` contain **536** records, with **428** train and **108** scan-disjoint engineering dev rows. Task01 contributes six training and two dev records per category; Task04 contributes 208 training and 52 dev per category. All prompts derived from one scan remain in the same split. Patient-level lineage is still unverified for both sources.

[`vero_official_launch.py`](../src/mri_rl/vero_official_launch.py) validates the source SHA and real image paths, then builds an official Hydra `gspo_qwen3vl` invocation. Its dry run succeeded, reporting 0.5/0.5 category weights and `proportional_equals_uniform=true`. An `--execute` attempt exited before training with `Official Vero training requires the requested CUDA GPUs`; local PyTorch reported **2.11.0 / `torch.cuda.is_available() == False`**. This is an actual hardware incompatibility for upstream veRL/vLLM, not a data-verifier gate. The M3 Pro MLX backend may allow a separate quantized LoRA research smoke, but would require a new implementation and must be labeled as such.

The MSD archives do not provide stable patient identifiers. Scan-disjoint engineering dev does **not** prove patient disjointness. The Task04 pair derives from one segmentation mask and has a 94.6% posterior majority class. Task01 has only eight scans; enhancing presence has a 6/8 positive majority at the fixed midpoint. Both task pairs share a source mask within each scan. These are valid task-routing and image-grounding engineering inputs, not independent clinical skills.

The combined data finally makes the **sampling mathematics** distinct: uniform category weights are 0.25 each; proportional weights are 208/428 = **0.4860** for each Task04 category and 6/428 = **0.0140** for each Task01 category. At the official batch size of 256, the pinned largest-remainder sampler would draw 64 prompts/category for uniform and approximately 124/124/4/4 for proportional. Uniform would recycle only six Task01 training scans heavily within a batch, so effective patient exposure and repeated-scan memorization must be logged; a model accuracy difference from this tiny pool would have no scientific interpretation. Both dry-run launcher arms passed schema/path checks, but neither updated weights.

CPU verification: `PYTHONPATH=src python3 -m pytest -q tests/test_vero_train_adapter.py` → **6 passed**; full repo suite **58 passed**. Training weights before/after: **not applicable; no optimizer step executed**.

[`mlx_gspo_smoke.py`](../src/mri_rl/mlx_gspo_smoke.py) is a separate Apple Metal feasibility path. It prepares the downloaded Qwen3-VL-8B model for 4-bit LoRA training, samples on-policy responses to a real MRI image, applies the pinned GSPO-token stop-gradient/clipping objective, refuses to optimize equal-reward groups, and would save private before/after adapter hashes if a nonzero-gradient update succeeds. This code was syntax and pure-math tested, but its model-loading, visual preprocessing, memory use, gradient execution and checkpoint reload are **unverified** until an actual Metal run. Quantization, rank-4 LoRA, a small group and compressed response budget are engineering departures from the official 8-GPU Vero recipe. Do not treat an eventual one-step smoke as cross-task transfer evidence.
