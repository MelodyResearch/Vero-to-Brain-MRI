## Consequences for interpreting completed runs

The zero-reward direct-format arms are consistent with a stringent tag/box gate and short local rollouts. The evidence does **not** isolate the cause: the run also changed prompt length, sample count, model precision, trainable parameter set, and step budget relative to official Vero. The post hoc single-box-anywhere updates bypass that strict gate and therefore cannot be called direct Vero GSPO success. SFT training and some local evaluations differ in their **system message**. They also pass different `enable_thinking` arguments to `apply_chat_template`, but an independent CPU tokenizer audit found that the pinned Qwen3-VL template does not reference that flag and renders identical bytes with the argument omitted versus `False`; the flag is **not an observed prompt mismatch for this checkpoint**. Compare rendered prompt/token IDs before treating format changes as learned behavior.

## MLX GSPO optimization parity boundary

The local `one_loss` in `mlx_gspo_smoke.py` has the key pinned source structure: mean response log-ratio, stop-gradient on that sequence ratio, token-wise current-log-prob gradient, the same asymmetric clipping, and mean token loss. Its `advantages_from_rewards` uses sample standard deviation (`n-1`) as the official GRPO helper does. These are **static code and CPU scalar checks**, not a gradient-equivalence test. No CPU numerical gradient comparison of the MLX autodiff graph against the PyTorch veRL graph was executed, and no CUDA optimizer parity test can run on this Mac. Further differences include a separate Adam initialized at every active group, frozen quantized base/vision parameters, and a different LR and token budget. The local update is therefore an MLX engineering approximation even when its scalar loss expression matches the pinned source. A meaningful parity gate would compare masked token log-probabilities, sequence ratios, clipping decisions, per-token gradients, and one-step parameter deltas on a tiny identical synthetic batch in both frameworks; this remains `NOT_RUN`.

## Focused CPU verification and next discriminating checks

`PYTHONPATH=src python3 -m pytest -q tests/test_vero_train_adapter.py` passed **15 tests** after the balanced-box change. The two added golden cases are in `tests/test_vero_train_adapter.py`. No GPU job was run for this audit.

Before another full RL arm, record for a small internal-dev/train-only sample: exact system prompt SHA, `enable_thinking` flag, rendered template suffix and token IDs, raw generated response, strict format/accuracy reward, and cap-hit fraction. Compare identical images/questions under (a) the official training prompt and training template mode, (b) the SFT prompt/template mode, and (c) a shorter local prompt as a diagnostic. Require nonzero variance in a bounded train-only group under the exact strict contract before attributing downstream changes to GSPO. If it remains zero, diagnose prompt/format adoption before increasing the group budget. Any full-recipe claim still requires a full-parameter compatible trainer or a clearly quantified adaptation study.
