# Independent MRI reward-contract review

**Reviewer:** Codex agent, independent read-only engineering review, 2026-10-15. **Scope:** the completed 28-update ds007045 SFT control, its first 54-question internal-development probe, the saved matched-prompt follow-up, local strict reward code, and historical direct-profile RL receipts. I did not run model inference or training, alter code or receipts, or publish private examples. Patient-linked files remain in ignored `local_data/`.

## Finding

The first SFT28 probe had a **prompt contract mismatch**: SFT trained every example with `SFT_SYSTEM_PROMPT`, while the original internal-dev manifest sent only the user message. The strict reward requires one complete `<think>...</think><answer>...</answer>` response. The original generated strings had no such tags; 48/54 included a box, and a *post hoc* box-anywhere extractor judged 35/54 answers correct. A bare correct box scores zero under the strict contract. Thus the 35 are semantic diagnostics, not 35 valid Vero-style rewards.

This is supported by a saved paired follow-up, not merely inferred from prompt text. The matched manifest prepends the exact SFT system message. Across all 54 record IDs, its SFT28 outputs use the **same adapter SHA, adapter config SHA, model path/config/template SHA, image SHA, category, 256-token cap, and temperature 0** as the original probe; the user question is identical. The changed manifest supplies the system message. Replaying the project scorer on both saved files gives:

| Probe | Strict format-valid | Strict task-correct | Box-anywhere task-correct |
| --- | ---: | ---: | ---: |
| First, user-only prompt, SFT28 | 0/54 | 0/54 | 35/54 (post hoc) |
| SFT-system-matched prompt, SFT28 | 54/54 | 36/54 | Not needed |
| SFT-system-matched prompt, starting adapter | 0/54 | 0/54 | Not assessed here |

The matched SFT28 strict-correct counts are sequence 15/24, tumor presence 10/12, enhancing presence 8/12, grid 3/6. The matched starting adapter's zero strict score demonstrates a format effect of the 28-update adapter under this prompt, but **does not** isolate gains in MRI interpretation. The 35 versus 36 semantic counts are from different prompts; they are not an accuracy gain estimate.

## Data path and reproducible failure

1. `src/mri_rl/mlx_sft_warmstart.py` defines the system instruction and passes it in training messages, then teacher-forces `<think>Visible MRI evidence.</think><answer>\boxed{...}</answer>`. Its private receipt records 28 optimizer updates, 112 examples from 28 training patients, nonzero gradients, and a changed saved adapter; the final adapter file SHA matches the receipt.
2. `src/mri_rl/ds007045_internal_dev_eval.py:61-66` builds the `original` manifest directly from each record's user-only `prompt`. The later `sft_train_matched` profile prepends the training system instruction. `src/mri_rl/frozen_eval.py:158-179` renders that manifest prompt and saves `response.text` and model/image/adapter receipts. It does not create a system message on its own.
3. `src/mri_rl/vero_mri_reward.py:40-64,104-129` requires the full tag pair before it can credit the final answer. A synthetic, label-free CPU reproduction against current code is:

   ```python
   from mri_rl.vero_mri_reward import compute_score_from_data_source
   base = dict(data_source="OpenNeuro_ds007045", ground_truth="FLAIR",
               extra_info={"reward_type": "mri_sequence"})
   compute_score_from_data_source(solution_str=r"\boxed{FLAIR}", **base)
   # {'score': 0.0, 'accuracy': 0.0, 'format': 0.0}
   compute_score_from_data_source(
       solution_str=r"<think>Visible MRI evidence.</think><answer>\boxed{FLAIR}</answer>",
       **base)
   # {'score': 1.0, 'accuracy': 1.0, 'format': 1.0}
   ```

This confirms why a semantically correct bare box cannot produce a strict reward. The saved paired output audit confirms that restoring the SFT instruction resolves *this probe's* wrapper absence. It does not prove a parser defect. The separately documented nested-box discrepancy had already been corrected in current reward code; none of the first probe's 54 responses had the required tags, so that issue cannot explain its zero strict score. The pinned tokenizer's `enable_thinking=False` was previously observed to render the same bytes as omission in this model; its presence in `frozen_eval.py` is not supported as the cause here. The saved probe receipts do not contain rendered prompt token IDs or generated-token boundaries, so those cannot be independently audited from these files.

## Minimal correction and regression gate

Make the SFT-system-matched manifest the explicit evaluation profile whenever testing this SFT control; bind the profile and exact system-prompt SHA to the run receipt and reject an SFT-format claim if either is missing or differs from training. Keep the user-only manifest as a named historical diagnostic. Do not silently relax the strict reward or substitute the box-anywhere extractor: that defines a different ablation.

The smallest regression test should construct synthetic train/dev rows, build both manifest profiles, and assert: (a) the matched manifest's system message is byte-identical to `SFT_SYSTEM_PROMPT` and the user question/image are unchanged; (b) a correct bare box receives strict score zero but a fully wrapped correct box receives one; (c) an SFT-format evaluation entrypoint refuses the original user-only profile. The current tests cover (a) and the reward gate in isolation, but there is no end-to-end guard that prevents an SFT-format claim from using the original profile again. For model-level verification, retain the existing same-adapter, same-image, same-decoder paired 54-row replay and assert a nonzero strict-format count; the saved follow-up gives 54/54. This is a CPU contract test plus an already completed inference check, not a request for another GPU run.

## Limits and scientific status

The three earlier direct-profile RL arms are **separate historical experiments**. They began from the four-step SFT adapter, used their own short/official system prompts, sampled 24 groups of two in total, and recorded 48 zero rewards, zero active groups, zero optimizer updates, and unchanged adapter hashes. The SFT28 manifest mismatch cannot retrospectively explain all of their zero rewards. It establishes a concrete failure mode for the *first SFT28 probe* and makes prompt/response contract alignment a prerequisite for any new strict RL rollout.

The matched SFT28 result establishes that the model can generate the strict format under its trained instruction on these internal-development questions. It does not establish image grounding, clinically useful reasoning, a balanced-task benefit, or GSPO transfer. The canned `Visible MRI evidence.` target is not evidence-specific. Same-prompt starting-adapter comparison, no-image and swapped-image controls, per-route label-prior checks, and an untouched patient cohort are still needed for scientific claims. Preserve the 0/54 first-probe and zero-update RL results as valid records of their exact protocols; do not overwrite or relabel them as successful training.

## Addendum: mandatory preflight review (Codex agent, CPU only)

I independently read `src/mri_rl/experiment_contract.py`, both substantial-run call sites, and their tests. I ran `PYTHONPATH=src python3 -m pytest -q tests/test_experiment_contract.py tests/test_real_mri_contract_integration.py`: **13 passed**. Neither a GPU model nor MLX was loaded. The SFT and multiarm entrypoints call `require_launch_preflight` before their own output-directory creation, MLX import, weight load, or child-process launch. A missing contract blocks both at that boundary. The static preflight checks manifest/artifact hashes, train/dev patient disjointness, decodable image files, a synthetic positive/negative strict reward, current resource status, and the declared prompt components. It explicitly leaves actual model-output and optimizer gates unverified.

The launch gate now requires a same-contract dynamic receipt, finite varying claimed task rewards, a positive claimed gradient, changed/reloaded claimed hashes, a hash-matched source receipt, and a review JSON bound to the dynamic-receipt SHA. For multiarm RL it also compares `dynamic.starting_adapter_sha256` with the actual launch adapter file. It rejects an interim Codex verdict or `NOT_VERIFIED`: the current literal check requires `reviewer_kind == "claude_code"` and `verdict == "PASS"`. The current `research/ENGINEERING_REVIEW_PROTOCOL.md` records the unpublished ds007045 Claude review as `NOT_VERIFIED` after an automatic sharing denial, so **this configuration is correctly blocked today**. `PASS_WITH_LIMITATIONS` is an allowed protocol verdict but is currently rejected for substantial launch; this is stricter than the requested PASS/PASS_WITH_LIMITATIONS policy and should be stated as a deliberate choice or changed with an explicit bounded-scope rule.

**Material remaining trust gap:** the gate verifies the *shape and consistency* of dynamic and reviewer files, not their provenance or scientific authenticity. In a disposable private CPU fixture I wrote a source receipt containing `{}`, a dynamic JSON asserting all seven gates with varying rewards and invented weight hashes, and a review JSON claiming `reviewer_kind: claude_code`, `verdict: PASS`, and a nonempty finding. After binding the required SHA fields and a start-adapter file, `require_launch_preflight` returned the contract ID. No real generation, gradient, reload, or Claude review occurred. This is a reproducible false positive for anyone able to author those private files; it must not be represented as an independently verified approval. The minimum safe launch procedure is to authenticate the permitted Claude review through an approved channel and independently recompute dynamic facts from actual immutable model/optimizer receipts and checkpoint bytes. The existing hash links alone provide integrity against accidental drift, not authorship.

**Scope bypass:** `src/mri_rl/mlx_gspo_smoke.py` still exposes a direct CLI and `run(...)` capable of a one-step weight update without calling this contract gate. The multiarm wrapper is gated, but a caller can bypass that wrapper and invoke the lower-level runner directly. If the rule is “all new weight-updating RL,” the lower-level runner needs the same gate or must accept a short-lived, validated authorization from the parent process. This was identified by code inspection; I did not invoke its GPU path.

**Static coverage limit:** `check_artifacts` hashes the supplied rendered prompt and token-ID files, but it does not recompute token IDs from that prompt or prove they came from the launch tokenizer. It checks that system instruction and diagnostic question text appear somewhere and that the prompt ends in the declared assistant prefix. The contract and artifact files can therefore be made mutually consistent yet wrong at the actual tokenizer/processor boundary. `materialize_local_contract` does generate a real local tokenizer specimen, but the launch gate validates saved specimens rather than rerendering at launch. A regression test should alter token IDs, recompute their contract hash, and require the gate to detect the semantic mismatch. This is separate from the dynamic-receipt trust gap and remains a CPU-verifiable test.
